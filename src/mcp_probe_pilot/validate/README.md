# Validate

Ensures every generated Gherkin step matches a canonical step pattern from the step library.

## Purpose

After feature files are generated by the LLM, they may contain step variations that don't have prebuilt implementations. The validator checks each step against the canonical step vocabulary and either normalises it to a known form or rejects it.

## Key Concepts

- **CanonicalStepRegistry** – Compiles every pattern from `core.canonical_steps.CANONICAL_PATTERNS` into regex matchers. Placeholders like `"{tool_name}"` become regex capture groups. Matching is case-insensitive.
- **Three-Outcome Classification** – Each step is classified as:
  - **Compliant** – directly matches a canonical pattern.
  - **Normalised** – doesn't match directly, but after applying text normalization rules it does. When `auto_fix=True`, the step text is rewritten in place.
  - **Rejected** – no canonical match even after normalisation. A fuzzy token-overlap heuristic suggests the closest pattern.
- **StepNormaliser** – Applies a priority-ordered list of regex substitution rules to bring LLM-generated step text closer to canonical form (e.g. "the response contains" → "the response should contain").
- **Auto-Fix** – When enabled, normalised steps are rewritten in the `GherkinFeatureCollection` so that downstream step generation can find existing implementations.
